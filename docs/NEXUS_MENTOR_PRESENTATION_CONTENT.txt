NEXUS - MENTOR PRESENTATION CONTENT
===================================

Purpose of this file
--------------------
This document contains ready-to-use content for a PowerPoint presentation about NEXUS.
Each section can be used as one or more slides. The wording is intentionally clear for a
mentor, evaluator, or project review.

IMPORTANT PROJECT POSITIONING
-----------------------------
NEXUS is an evidence-first investigative decision-support prototype using synthetic data.
It is not connected to real police, intelligence, telecom, financial, or surveillance systems.
It must not be used with real criminal or personally identifying data.

NEXUS does not prove criminality. Relationships, anomalies, graph scores, and model outputs
are analytical leads that require human verification, source review, authorization, and
applicable legal process.

The current implementation contains ONE actual machine-learning algorithm:
- Isolation Forest for unsupervised anomaly screening.

The project also contains five important deterministic or algorithmic workflows:
1. Rule-based NLP/entity extraction using regular expressions.
2. Fuzzy entity resolution using RapidFuzz.
3. Explicit relationship extraction from structured records and text.
4. NetworkX graph analytics: degree, betweenness, communities, and shortest paths.
5. Evidence-grounded retrieval Copilot using local case data and graph results.

These six workflows may be presented as the six analytical workflows of NEXUS, but only
Isolation Forest should be described as machine learning. This distinction is important for
technical accuracy.

NEXUS - Evidence-First Investigative Intelligence

Presenter points:

SLIDE 2 - PROBLEM STATEMENT
----------------------------
Problem:
Investigative information is often fragmented across different files and record types.
An investigator may need to compare:
- Call-detail records.
- Financial transactions.
- Person and vehicle records.
- Location and visit events.
- Reports, FIRs, TXT, PDF, and DOCX documents.
- Relationship timelines and supporting evidence.

Challenges:
- The same entity may appear with different identifiers or names.
- Important relationships may be hidden across separate records.
- Large tables are difficult to analyze manually.
- Anomalous patterns can be difficult to notice.
- Analytical conclusions must remain connected to original evidence.

NEXUS response:
Create a case-scoped, evidence-linked workspace that normalizes source records, resolves
entities, builds a relationship graph, supports temporal analysis, and highlights patterns
for human review.


SLIDE 3 - PROJECT OBJECTIVES
----------------------------
1. Ingest synthetic records from CSV, JSON, TXT, PDF, and DOCX sources.
2. Store source evidence and preserve provenance.
3. Extract entities such as people, vehicles, phones, money, dates, locations, and accounts.
4. Resolve repeated references to the same entity.
5. Build explicit relationships with timestamps, confidence, and evidence IDs.
6. Display connections through a visual network graph.
7. Provide timeline analysis for relationship events.
8. Detect unusual network activity using Isolation Forest.
9. Provide evidence-grounded local Copilot responses.
10. Keep findings in a human-verification state.

SLIDE 8 - WORKFLOW 1: RULE-BASED NLP / ENTITY EXTRACTION
----------------------------------------------------------
Purpose:
Extract recognizable entities from unstructured text documents.

Technology:
- Python regular expressions.
- Deterministic patterns.
- No external language model is required.

Current patterns:
- PERSON: capitalized one-to-three-word names.
- VEHICLE: Indian-style registration patterns such as MH12AB1234.
- PHONE: Indian phone-number pattern, including optional +91.
- MONEY: rupee and Rs. amount patterns.
- DATE: common numeric and month-name date patterns.

Relationship extraction from text:
- "Person A called Person B" becomes CALLED.
- "Person A contacted Person B" becomes CALLED.
- "Person A met Person B" becomes SEEN_WITH.
- "Person A was seen with Person B" becomes SEEN_WITH.

Strengths:
- Fast, deterministic, explainable, and offline.
- Easy to test and audit.

Limitations:
- It is not full natural-language understanding.
- It may miss aliases, spelling variations, complex sentences, or ambiguous names.
- Extracted relationships remain source-derived and require review.


SLIDE 9 - WORKFLOW 2: ENTITY RESOLUTION
-----------------------------------------
Purpose:
Decide whether two references represent the same entity.

Technology:
- RapidFuzz similarity ratio.
- Exact matching for numeric identifiers such as phone numbers and account IDs.
- Entity type and case scope are used during matching.

Process:
1. Normalize the incoming name or identifier.
2. Search existing entities in the same case and type.
3. For numeric identifiers, require exact equality.
4. For text names, calculate fuzzy similarity.
5. Reuse an entity when similarity reaches the configured threshold.
6. Otherwise create a new entity.
7. Store resolution confidence in metadata.

Why exact numeric matching matters:
Two phone numbers that differ by one digit are different identifiers. Fuzzy merging them
would create false people and incorrect relationships.

Example:
- 9876500001 and 9876500002 must remain separate entities.
- Rahul Sharma and R. Sharma may require a future alias-aware resolver.

Limitations:
- Fuzzy matching can still produce false positives for similar names.
- Production deployment would need stronger identity keys, alias tables, review queues,
and domain-specific matching rules.


SLIDE 10 - WORKFLOW 3: RELATIONSHIP EXTRACTION
-----------------------------------------------
Purpose:
Create graph edges only when the source record explicitly supports a semantic relationship.

Structured relationship rules:
- caller + receiver -> CALLED.
- sender + receiver -> TRANSFERRED.
- owner + vehicle_id or registration -> OWNS.
- person/person_id + location -> VISITED.
- vehicle_id/registration + location -> LOCATED_AT.

Every relationship contains:
- Relationship ID.
- Case ID.
- Source entity ID.
- Target entity ID.
- Relationship type.
- Confidence value.
- Timestamp or date.
- Source evidence ID.
- Verification state, initially pending.

Important correctness rule:
The system does not connect the first two arbitrary entities in a row. It maps relationships
from named fields. For example, a financial record with sender, receiver, and location does
not automatically prove that the sender visited the location.

This protects the graph from false person-to-location and person-to-vehicle links.


SLIDE 11 - WORKFLOW 4: GRAPH ANALYTICS
---------------------------------------
Purpose:
Make indirect relationships and network structure easier to inspect.

Technology:
- NetworkX graph library.
- FastAPI graph endpoints.
- Cytoscape.js frontend visualization.

Graph contents:
- Nodes represent entities.
- Edges represent source-backed relationships.
- Edge metadata includes type, confidence, timestamp, evidence ID, and verification.

Current metrics:
1. Degree centrality
   - Measures how many direct connections an entity has relative to the graph.

2. Betweenness centrality
   - Measures how often an entity lies on shortest paths between other entities.

3. Connected communities/components
   - Groups entities that are connected through graph relationships.

4. Shortest paths
   - Shows a possible relationship path between two entities with evidence details.

Frontend graph behavior:
- Person, vehicle, location, and other entity types have distinct visual styles.
- Clicking an entity opens the inspector.
- The inspector is intended to show source-linked details rather than conclusions.

Interpretation warning:
High centrality does not mean guilt or importance in a criminal sense. It only describes
the structure of the recorded graph.


SLIDE 12 - WORKFLOW 5: ISOLATION FOREST ANOMALY SCREENING
-----------------------------------------------------------
This is the actual machine-learning workflow.

Purpose:
Identify entities whose relationship activity differs from the case baseline.

Algorithm:
- Isolation Forest from scikit-learn.
- Unsupervised learning.
- No labeled training set is used in the current synthetic prototype.
- 100 estimators.
- Random state 42 for repeatability.
- Contamination is set to auto.

Input features per entity:
1. interaction_count
   - Number of outgoing relationships recorded for the entity.

2. unique_contacts
   - Number of distinct target entities.

3. night_interaction_count
   - Number of relationships occurring before 06:00 or at/after 22:00.

4. mean_confidence
   - Average relationship confidence for the entity.

Feature workflow:
1. Start with the case entity IDs.
2. Read case relationships.
3. Count outgoing interactions.
4. Track unique targets.
5. Parse timestamps and count night activity.
6. Aggregate confidence values.
7. Create a Pandas feature table.
8. Fit Isolation Forest.
9. Generate predictions and decision scores.
10. Keep entities predicted as -1 as anomaly leads.
11. Convert the score to a bounded 0-to-1 screening score.
12. Generate human-readable reasons by comparing features with the case median.

Possible explanation reasons:
- Unusually high communication volume.
- Unusually high number of unique contacts.
- Unusual late-night activity.
- Feature combination differs from the case baseline.

Output:
- Entity ID.
- Screening score.
- Medium or high severity.
- Explanation reasons.
- Feature values used by the model.

Limitations:
- Anomaly is not wrongdoing.
- Synthetic data has no labeled ground truth.
- The score is a screening aid, not an accuracy claim.
- The current feature set is small.
- Production use would require governance, validation, drift monitoring, fairness review,
proper labels, and domain approval.


SLIDE 13 - WORKFLOW 6: EVIDENCE-GROUNDED COPILOT
-------------------------------------------------
Purpose:
Allow an investigator to ask simple questions using local case data.

Technology:
- Local Python service.
- SQLite retrieval.
- Existing graph path and graph metric functions.
- No external AI model or external data connection is required.

Supported reasoning patterns:
1. Relationship/path questions
   - Finds named entities in the question.
   - Requests a graph path.
   - Returns path steps and evidence IDs.

2. Centrality questions
   - Returns graph metrics for central or connecting entities.

3. Anomaly questions
   - Returns current case anomaly leads.

4. General help questions
   - Returns counts of relationships and evidence records.

Grounding:
- Local NEXUS graph.
- Local SQLite evidence database.
- Local case workspace only.

Safety design:
- Answers refer to evidence and analytical leads.
- The Copilot does not claim criminality.
- The investigator must inspect source evidence and verify the result.

SLIDE 17 - EVIDENCE AND VERIFICATION MODEL
-------------------------------------------
NEXUS follows an evidence-first principle:
- Every uploaded source is preserved as an evidence record.
- Relationships keep the source evidence ID.
- Timestamps are retained where supplied by the source.
- Confidence indicates extraction/resolution confidence, not truth.
- Verification begins in a pending state.
- Investigators must review source material before treating a finding as reliable.

Correct interpretation examples:
- Correct: "The record contains a CALLED relationship between two identifiers at this time."
- Incorrect: "The person is criminal because the graph shows a call."

- Correct: "The model marked this activity as unusual relative to the case baseline."
- Incorrect: "The model proved illegal behavior."

SLIDE 20 - CURRENT LIMITATIONS
------------------------------
1. Data is synthetic only.
2. There is no connection to real institutional systems.
3. The current ML model is unsupervised and has no labeled accuracy claim.
4. The NLP extractor is regex/rule based.
5. Entity resolution is not a complete identity-resolution system.
6. Location data is evidence-based and may contain place names without GPS coordinates.
7. Phone numbers alone are not used as live location tracking.
8. Demo authentication is not production security.
9. SQLite is appropriate for a local prototype, not necessarily distributed production scale.
10. Neo4j assets are future-deployment scaffolding, not the active graph database.
11. Human verification and legal authorization are required for real-world use.

SLIDE 22 - CONCLUSION
---------------------
NEXUS demonstrates how fragmented synthetic records can be transformed into an evidence-
linked investigative workspace.

The system combines:
- FastAPI APIs.
- React/Vite interface.
- SQLite persistence.
- Pandas feature engineering.
- NetworkX graph analytics.
- RapidFuzz entity resolution.
- Rule-based NLP extraction.
- scikit-learn Isolation Forest anomaly screening.
- Evidence-grounded local Copilot.
- Human verification and audit scaffolding.

The main value is traceability:
An investigator can move from a visual relationship or anomaly lead back to the timestamp,
source record, evidence ID, and original content.

Final message:
NEXUS is a decision-support prototype. It organizes evidence and highlights patterns; it
does not make accusations or replace investigators, legal process, or institutional review.
